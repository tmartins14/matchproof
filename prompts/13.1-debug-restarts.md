# Build prompt 13.1 — Find why the API container restarts mid-match, then fix it

**Mode:** debug, then code. **Budget:** 2 hours. Stop and report at the 2-hour mark if the cause isn't proven. **Branch:** `fix/api-restarts`. **Depends on:** PRs 30–32 merged. **Blocks:** M3, and prompt 14, because cached replays stream the same way.

## What we know

Read `docs/DEPLOY.md` § Known issue first. In short:

- **Restarts:** the API container restarted in place twice on Oct 25, at 19:34:05 and 20:19:44 UTC, each about 2 minutes into a live match at 6× with agents running. The desk showed "Connection lost."
- **No cause in the logs:**
  - `ContainerAppSystemLogs_CL` and `ContainerAppConsoleLogs_CL` show no exit code, no OOM event and no traceback;
  - the last console line before each restart is a normal model-call response, and the next is a fresh `uvicorn` start.
- **Resources:** memory was about 460–510 MiB of 2 GiB and CPU about 25% at the last 1-minute sample, which can hide spikes.
- **Health check:** `GET /health` does almost nothing, yet averages about 5.8 s from the availability tests. The app is slow to answer even trivial requests.
- **Earlier success:** one match did reach full time on the same app, 2–0 at 98:04, but on an archived id with only 2 claims, so with much less agent work.
- **Shape of the app:** one `uvicorn` process with one worker on 1 vCPU. The live pipeline runs on a worker thread, and the agents make model calls through the async runtime. Infra defines no custom probes, so Container Apps uses its defaults.
- **Ingress:** Container Apps ingress has a 240-second request timeout (from the ingress docs, cited in PR 31). Streams run several real minutes, and the smoke test only streams 30 s.

## Hypotheses, in order of likelihood

1. **Health probe failure.** The process stops answering in time while a match plus its agents run (GIL contention, or blocking work on the event loop), the platform's default probe fails a few times in a row, and the container is restarted. That fits "restart in place, no exit code, no OOM" and the 5.8 s `/health`.
2. **Memory spike above the real cgroup limit**, between the 1-minute samples. The effective limit may not be 2 GiB.
3. **Ingress cutting the stream at 240 s**, separate from the restart. That would explain some "Connection lost." cases, but not the `uvicorn` restart.
4. Something else.

## Part A — Measure. No fixes yet.

1. **Effective config.**
   - Run `az containerapp show` and `az containerapp revision show` for the active revision, and paste the probes block: liveness, readiness and startup, with type, path or port, `timeoutSeconds`, `periodSeconds` and `failureThreshold`.
   - If it's empty, find in Microsoft Learn what Container Apps applies by default when ingress is enabled, cite the page, and state the defaults.
   - Paste the container's resources and replica settings.
2. **Instrumentation** (small, keep it in the PR). Add to the API:
   - At startup, log `/sys/fs/cgroup/memory.max`, `/sys/fs/cgroup/cpu.max`, the PID and the Python version.
   - Every 5 s, from a background asyncio task, log one structured line:
     - **memory:** RSS (from `/proc/self/status`), `memory.current` and peak from cgroup;
     - **CPU:** process CPU % since the last line;
     - **event-loop lag:** the scheduled sleep versus the actual wake-up, in ms;
     - **load:** thread count, open streams, `ledger.pending`.
   - **Signals and crashes:** a SIGTERM handler that logs "SIGTERM received" with the same numbers, then lets `uvicorn` shut down normally, and `faulthandler.enable()` for hard crashes.
   - A trivial `GET /livez` (`async def`, returns `{"ok": true}`, touches nothing). Don't point any probe at it yet.
3. **Local reproduction, with agents.**
   - Run `make api-dev` with `taskset`/`cpulimit`, or Docker `--cpus=1 --memory=2g` to match prod.
   - Play one live match at 6× to full time, while polling `/health` and `/livez` every 2 s and logging the latency.
   - Report the event-loop lag distribution (p50, p95, max), the max RSS, and the slowest `/health` and `/livez` responses.
4. **Production reproduction.**
   - Deploy the instrumentation (`azd deploy api`).
   - Play one live match at 6× from the desk, while polling `/livez` and `/health` every 2 s from your machine with timestamps. Also capture the raw stream with timestamps:
     ```
     curl -sN "$API_URL/matches/<id>/stream?speed=6" | while IFS= read -r l; do echo "$(date +%s.%N) $l"; done > stream.log
     ```
   - If it restarts, collect the 5-second lines before the restart, the system log entries around it (probe events, restart reason) and the stream's last line. Then line up three timestamps:
     - the stream's start;
     - its drop;
     - the restart.
   - Note in particular whether the drop is about 240 s after the stream started.

## Part B — Decide

Write the root cause in the PR, with the evidence lines quoted. Then apply **only** the fix the evidence supports:

- **Probe failure plus event-loop lag:**
  - **Probes:** add explicit probes in `containerapp.bicep`:
    - liveness: HTTP `GET /livez`, timeout 5 s, period 10 s, failure threshold 6;
    - readiness: HTTP `GET /livez`, timeout 5 s, period 5 s;
    - startup: generous enough for the image's cold start.
  - **Event-loop lag:** find and remove what blocks the loop. Every CPU-heavy call reachable from an `async def` goes to a thread (`asyncio.to_thread`) or a process. List each one you moved.
  - **Capacity:** if p95 lag stays above 1 s, propose 2 vCPU / 4 GiB in Bicep with its monthly cost (`minReplicas: 1`, from the pricing page), and say whether it's needed.
- **Memory:** if the cgroup limit is lower than assumed or there's a spike, find the allocation (frames held in lists, the archive save, the registry copy) and stream or chunk it. Re-measure.
- **Ingress 240 s:** make the stream resumable with agents:
  - The match run keeps every message it sent (seq → message) for the match's life.
  - A reconnect with `Last-Event-ID` replays the gap from that buffer and continues the **same** run. Agents are never restarted and nothing is re-narrated.
  - The desk reconnects automatically with `Last-Event-ID` (at most 3 attempts, 1 s apart) and shows nothing extra on a successful reconnect.
  - Test: cut a stream at a fixed seq mid-beat, reconnect, and assert the full sequence equals an uncut run.
- **Several causes:** fix each one, in separate commits.
- **Unproven at 2 hours:** don't guess. Keep the instrumentation, write down what was ruled out and what remains, and stop.

## Rules

- Don't raise `minReplicas`, timeouts or container size "just in case". Any resource change needs its cost and its evidence.
